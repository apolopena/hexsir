# Creating a New CLI Tool

[← Back to Tools](README.md)

New CLI tools are created through [scafcli](scafcli.md), which bootstraps a fully working, self-documented tool that enforces the project's opinionated structure — code layout, file conventions, and coding standards — so it's ready to extend from the first commit. Every tool created through scafcli shares the same structure, output patterns, test setup, and documentation, so new tools fit cleanly alongside existing ones from day one.

This guide walks through creating a tool, understanding what gets generated, and extending it.

`scafcli` provides:

- Directory layout and Click wiring
- Bash wrapper with env var defaults
- Test foundations and lint configuration
- Shared library dependencies
- CHANGELOG and version tracking

### ⚠️ `backend-lib` — optional business logic module

> If this repo was scaffolded with `--no-backend-lib`, the `--include-backend` flag is unavailable and `backend-lib` related content in this document does not apply.

## Quick Start

Create a tool:

```bash
just tool-new demotoolcli mycommand
./tools/demotoolcli --version
# -> demotoolcli 0.1.0 (dev source)
```

With backend libraries and env var infrastructure (HTTP client, auth, fail-fast validation):

```bash
just tool-new demotoolcli mycommand --include-backend
```

With REPL interactive session:

```bash
just tool-new demotoolcli mycommand --include-repl
```

With both — the common choice for REPL-based tools that need backend libraries and environment variables:

```bash
just tool-new demotoolcli mycommand --include-backend --include-repl
```

Interactive mode (prompts for all options):

```bash
just tool-new
```

Add a command to an existing tool:

```bash
scafcli tool add command demotoolcli mynewcommand
```

## Naming Rules

- **Tool names** must be lowercase letters only, ending in `cli`. No digits or hyphens.
- **Command names** must be lowercase letters and hyphens, with no leading or trailing hyphens.

## How Tools Work

`scafcli` handles the setup. Here's what it builds and why.

### Self-contained by design

Each tool is a self-contained Python package. Scaffolded tools place commands in `commands/`, application code in `lib/`, non-code assets in `data/`, and tests in `tests/`. A tool must not depend on data files outside its own directory. Configuration is done exclusively through environment variables.

This matters because tools are deployed as standalone CLIs on PATH via `uv tool install`. If a tool reaches outside its directory for data or config, it breaks the moment it leaves the repo.

### Two execution modes

Tools run either through a bash wrapper or as a standalone CLI on PATH. The Python code is identical in both.

**Standalone CLI** (`demotoolcli`): A standalone Python package on `PATH`. No wrapper, no defaults. `--version` always works regardless of env vars. For backend tools, missing env vars cause an immediate exit — see [Output and errors](#output-and-errors) below.

**Bash wrapper** (`./tools/demotoolcli`): A bash script that sets `TOOL_EXEC_MODE=dev-source`, exports all required env vars with localhost defaults, and execs the tool's Python entry point.

### Why the bash wrapper exists

1. **Develop, compare, ship** -- develop against the bash wrapper, compare behavior with the installed version, and ship when ready. Both can run simultaneously so you catch regressions before they reach users.
2. **Zero-config local development** -- the wrapper exports all required env vars with localhost defaults. `./tools/demotoolcli` just works, no setup.

### No filesystem walking in deployed tools

Deployed tools must not walk the filesystem for paths. All paths come from environment variables or arguments. Tools that need the project root use `CLI_ROOT_DIR` — the bash wrapper sets it automatically, and standalone CLIs require the user to export it.

## What Gets Created

```
tools/demotoolcli-src/
  cli.py              <- Click group with --version, command registration
  commands/
    __init__.py       <- module docstring
    mycommand.py      <- initial command stub with _cmd suffix
  pyproject.toml      <- version 0.1.0, deps on display-lib (+ backend-lib, repl-lib if flagged)
  uv.lock             <- generated by uv sync, tracks resolved dependencies
  lib/
    __init__.py       <- empty, add your business logic here
    paths.py          <- canonical get_root_dir() boilerplate
  data/
    __init__.py       <- empty, add schemas/templates/seeds here
  tests/
    conftest.py       <- env var defaults, integration marker
    unit/
      __init__.py
      test_cli.py     <- smoke tests (--version, --help)
      test_mycommand.py  <- command tests (runs, help)
  CHANGELOG.md        <- initialized with 0.1.0 Unreleased
tools/demotoolcli      <- bash wrapper (executable)
```

## Adding a Command

Use `scafcli tool add command` to generate the command file and test, and auto-wire it into `cli.py`:

```bash
scafcli tool add command demotoolcli mynewcommand
```

This creates `commands/mynewcommand.py` and `tests/unit/test_mynewcommand.py`, and inserts the import and registration into `cli.py` via the `[auto] scaffold:*` markers. For REPL tools, it also wires into `_CLICK_COMMANDS`. Help text is auto-generated from the command's docstring.

If a tool has no markers in `cli.py`, it generates the files and prints the lines to add manually. For the manual registration pattern, see [coding-standards.md > Click conventions](coding-standards.md#click-conventions).

## Understanding the Generated Code

`scafcli` generates working code that follows specific patterns. This section covers what you need to know about each area to work with and extend the generated code effectively.

### Directory structure

The layout is the same for every tool — commands in `commands/`, business logic in `lib/`, assets in `data/`. The entry point is always `cli.py` (never `__main__.py`). For the full convention details, see [coding-standards.md > Directory layout](coding-standards.md#directory-layout).

### Bash wrapper

The generated wrapper at `tools/demotoolcli` handles venv resolution, env var defaults, and exec. It follows a strict pattern — `set -euo pipefail`, `TOOL_EXEC_MODE` export, and `exec` to replace the shell process. For the full wrapper conventions, see [coding-standards.md > Bash wrappers](coding-standards.md#bash-wrappers).

### Click entry point

`cli.py` is registration and boilerplate only — version callback, `check_env` guard, command imports, and `add_command` calls. All command logic lives in `commands/`, one file per command. Commands use the `_cmd` suffix (`billing_cmd`, `check_status_cmd`) and are registered as kebab-case (`billing`, `check-status`). For the full Click conventions, see [coding-standards.md > Click conventions](coding-standards.md#click-conventions).

### Backend (if `--include-backend`)

`scafcli` generates env var infrastructure across three files: `REQUIRED_VARS` + `check_env()` in `cli.py`, `export` lines with localhost defaults in the bash wrapper, and `os.environ.setdefault()` entries in `tests/conftest.py`. This wiring is automatic — the tool works immediately in dev, fails fast in production if vars are missing, and tests run without manual setup.

To add a custom env var beyond the standard set, prefix with the tool name to avoid collisions (e.g., `DEMOTOOLCLI_BACKEND_URL`) and update three files: `REQUIRED_VARS` in `cli.py`, the `export` in the bash wrapper, and the `setdefault` in `tests/conftest.py`. For the full list of what the flag generates, see [coding-standards.md > Scaffold flags](coding-standards.md#scaffold-flags).

### REPL (if `--include-repl`)

`scafcli` generates a minimal sync REPL dispatch with `repl-lib`. Commands are registered in `_CLICK_COMMANDS` and dispatched via Click's context system. The REPL auto-generates help from each command's docstring — no manual help registration needed.

For tools with async commands and session state, you'll extend the generated dispatch with `_ASYNC_FNS`, `_NEEDS_SESSION`, and session builtins. The REPL also supports optional validator callbacks on builtins for input validation (e.g., confirming a session ID exists before storing it). For the full dispatch pattern, session state, and validator details, see [coding-standards.md > REPL dispatch](coding-standards.md#repl-dispatch).

### Scaffold markers

`scafcli` inserts `# [auto] scaffold:imports` and `# [auto] scaffold:commands` comments in `cli.py`. These are insertion points used by `scafcli tool add command` to auto-wire new commands. Do not remove them. REPL tools also have `# [auto] scaffold:repl-commands`. See [coding-standards.md > Scaffold markers](coding-standards.md#scaffold-markers).

### Shared packages

Every tool depends on `display-lib`. The `--include-backend` flag adds `backend-lib` (HTTP client, auth, DB queries), and `--include-repl` adds `repl-lib` (REPL dispatch, history, builtins). `tree-lib` is added manually when a tool needs structured tree rendering or task execution with pass/fail output. Every scaffolded tool also gets `test-lib` as a dev dependency — it provides `assert_cli_ok(result)` for Click CLI test assertions with diagnostic output on failure. Shared libraries are linked as editable dependencies so changes are immediately visible during development. For the complete library reference and packaging details, see [coding-standards.md > Shared Libraries](coding-standards.md#part-2-shared-libraries).

### Output and errors

Use `display_lib.output` functions for all terminal output: `success()`, `error()`, `info()`, `warn()`, `header()`, `dim()`. Only two symbols: checkmark (success) and X (error). Use `spin()` for async spinners and `Spinner` for sync spinners. Always check HTTP status codes. Use `sys.exit(1)` for fatal errors, but `return` in REPL mode.

For structured hierarchical output, use `tree-lib`. It provides `render_tree()` for explicit node hierarchies, `render_tree_from_paths()` for path-based trees, and `run_task()` for executing operations with pass/fail tree output and optional spinners. If your tool shows progress on a sequence of operations, use `run_task` — don't build spinner + tree output manually. Add `tree-lib` to your `pyproject.toml` dependencies when needed — follow the editable dependency pattern in [coding-standards.md > Packaging](coding-standards.md#packaging).

For the full output function reference, tree-lib API, and error handling patterns, see [coding-standards.md > Output, colors, and tree rendering](coding-standards.md#output-colors-and-tree-rendering) and [Error handling](coding-standards.md#error-handling).

### Environment variables

Tools read all configuration from the process environment (`os.environ`). They never parse `.env` files directly. In dev, the bash wrapper exports URL vars with localhost defaults. Secrets (`AGENT_STREAM_JWT_SECRET`, `INTERNAL_SERVICE_SECRET`) are not in the wrapper — they live in the project's `.env` file and must be sourced into the shell by the developer. For standalone CLIs, all vars must be exported by the user. Custom variables use the tool name as a prefix to avoid collisions (e.g., `DEMOTOOLCLI_BACKEND_URL`).

| Variable | Purpose | Set by | Required |
|----------|---------|--------|----------|
| `TOOL_EXEC_MODE` | `dev-source` when running via wrapper | Bash wrapper | all tools |
| `CLI_BACKEND_URL` | Main backend URL | Bash wrapper (dev) / user export (standalone) | `--include-backend` |
| `CLI_AGENTIC_BACKEND_URL` | Agentic backend URL | Bash wrapper (dev) / user export (standalone) | `--include-backend` |
| `CLI_AGENTIC_BACKEND_WS_URL` | WebSocket URL for agent streaming | Bash wrapper (dev) / user export (standalone) | `--include-backend` |
| `AGENT_STREAM_JWT_SECRET` | JWT secret for agent streaming auth | Project `.env` (sourced by developer) | `--include-backend` |
| `INTERNAL_SERVICE_SECRET` | Internal service auth secret | Project `.env` (sourced by developer) | `--include-backend` |

### pyproject.toml

`scafcli` generates a complete `pyproject.toml` with all required sections. The most important sections to understand are `[project.scripts]` (CLI name), `[tool.uv.sources]` (shared library links), and `[tool.coverage.run]` (test coverage scope). For the full section reference with required vs optional breakdown, see [coding-standards.md > pyproject.toml](coding-standards.md#pyprojecttoml).

For tools with significant integration code, see [coding-standards.md > Coverage ratings for integration-heavy tools](coding-standards.md#coverage-ratings-for-integration-heavy-tools).

After any change to `pyproject.toml`, sync immediately:

- **Single tool changed:** `just tool-sync <name>`
- **Shared library changed:** `just tool-sync-all`

### Changelog

`scafcli` initializes `CHANGELOG.md` with a `0.1.0 Unreleased` entry. Every change to a tool or shared library gets a version bump and a corresponding changelog entry — even on unreleased branches. See [coding-standards.md > Version Discipline](coding-standards.md#important-version-discipline) for the semver rules.

## Testing

Each tool has its own venv and its own test suite.

```bash
# Before registering in run-tests.sh -- run pytest directly:
cd tools/demotoolcli-src && .venv/bin/pytest tests/ -v
just tool-lint demotoolcli                      # lint works immediately
```

- Tests in `tests/unit/` and optionally `tests/integration/`
- `conftest.py` sets env var defaults with `os.environ.setdefault()`
- Integration marker: `config.addinivalue_line("markers", "integration: ...")`

## Registering in the Test Runner

Optional. To include your tool in `just tool-test <name>` and `./scripts/run-tests.sh -c` runs, add your tool name to the `CLI_TOOLS` array in `scripts/run-tests.sh`:

```bash
    "demotoolcli"
```

`scafcli` prints this exact line after creating your tool. No Justfile registration is needed — `_get-tool-src-dir` is convention-based.

## Packaging

```bash
just tool-install demotoolcli                   # install as standalone CLI on PATH
demotoolcli --version                           # -> demotoolcli 0.1.0
```

## Smoke Testing

Verify your tool installs and runs as a standalone CLI on PATH:

```bash
just tool-smoke-test demotoolcli
```

This installs the tool, checks `--version` and `--help`, then uninstalls.

## What scafcli Provides

When you run `just tool-new`, `scafcli` generates:

- Tool name validated against naming rules (lowercase letters only, ends in `cli`)
- `pyproject.toml` with correct name, version, and all required sections
- `uv.lock` synced with `pyproject.toml`
- Bash wrapper at `tools/<name>` (executable, venv resolution, env var defaults)
- Scaffold markers in `cli.py` (`[auto] scaffold:imports`, `[auto] scaffold:commands`)
- `--version` working via both bash wrapper and standalone CLI
- `CHANGELOG.md` initialized with `0.1.0 Unreleased`
- Passing tests: `just tool-test <name>`
- Clean lint: `just tool-lint <name>`
