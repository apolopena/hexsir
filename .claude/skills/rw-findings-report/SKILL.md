# rw-findings-report

Creates a findings document for Ravenswatch RE analysis. Findings live in a single flat directory with a status field that flips as the work matures: `in-progress` → `confirmed` → `archived`. Promotion is editing the status line, not moving the file.

## When to invoke

Trigger on phrases like:
- "create a findings report"
- "create a finding for this"
- "make a triage doc" / "create a triage report" (legacy phrasing — same artifact)

## What it does

1. **Determine sources.** From the conversation context, identify which files were analyzed (saves, harvested binaries, dumps, etc.). If unclear, ask the user.

2. **Determine filename.** Use a kebab-case slug describing the subject (e.g., `geppetto-save-format.md`, `entity-binary-strings.md`). Ask if not obvious.

3. **Check for slug collision.** Before creating the file, verify `rw/findings/<slug>.md` does not already exist. If it does, **stop and surface the collision** — do NOT overwrite. Findings docs are topic-focused; if a topic already has a doc, the right action is to edit it in place (or extend its `## Unresolved` / `## Notes` sections), not to create a sibling. Tell the user the existing doc's path and its current `**Status:**` line, then ask whether to (a) update the existing doc, (b) pick a different slug for a genuinely separate topic, or (c) abort. Never silently clobber.

4. **Create the file** at `rw/findings/<slug>.md`. Required sections only — omit any section without real content:

**Always include:**

```markdown
# <Title>

**Status:** in-progress
**Created:** <YYYY-MM-DD>

## Sources

- <relative path to source file 1>
- <relative path to source file 2>
```

The `**Status:**` line MUST match `^\*\*Status:\*\* (in-progress|confirmed|archived)$` exactly — `rw/findings/STATUS.md` is regenerated by greping for that line. New findings always seed `in-progress`.

**Then include only the sections that apply:**

- `## Confirmed Findings` — facts with evidence. Skip if there's nothing confirmed yet.
- `## Unresolved` — open questions, partial leads. Skip if everything is confirmed.
- `## Notes` — context, methodology. Skip if not adding value.

A finding doc with only confirmed observations is fine. A doc with only unresolved questions is fine. Don't pad sections to fit a template.

5. **Fill in only the sections with real content** based on the conversation. Be honest about what's confirmed vs speculative — that's the whole point of a status-tracked finding.

6. **Use relative paths** for sources (relative to repo root), so they remain valid as files move.

## Workflow context

Findings docs are tracked in git. They sit between raw `dumps/` (untracked working outputs) and the final code/CLI/tests that bake in confirmed knowledge.

Status lifecycle: `in-progress` → `confirmed` (claims independently verified) → `archived` (superseded; banner explains what replaced it). Status is edited in place — the file path never changes.

See `rw/docs/workflow/README.md` for status-field semantics, and `rw/findings/README.md` for the directory-level overview.

## Constraints

- Do NOT invent findings. Only document what the conversation supports.
- Do NOT promote anything to `confirmed` from this skill — that's a separate review step.
- Always include the Sources section, even if it's a single file.
- Keep the file tight. Findings docs accumulate cruft fast; don't add filler.
